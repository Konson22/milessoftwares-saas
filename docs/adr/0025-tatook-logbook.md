# ADR-0025: Tatook Logbook, a standalone application

Status: **Accepted (2026-11-19). Web MVP built locally, not deployed.**
Follows the standalone precedents ADR-0019 (M&E) and ADR-0023 (Procurement).

Tatook Logbook is a configurable digital logbook. It replaces paper log sheets and Excel registers with records that have a structure, a review and an audit trail. Slogan: *Every activity recorded. Every record accounted for.*

## 1. Assessment (verified in code, 2026-11-19)

| Question | Finding |
|---|---|
| Stack | One repository. Each product is a Laravel 13 + Inertia 3/React 19 app generated by `templates/new-product.php`, with its own PostgreSQL database, php-fpm pool and catalog. Shared UI is `@miles/ui` (shell, page header, panel, stat card, status badge, shadcn primitives). Wayfinder generates typed routes. |
| Identity and SSO | Central is the OIDC provider. `platform-client` signs members in with PKCE on the workspace host (`{slug}.milessoftwares.com/{code}`). Products hold no passwords. |
| Tenancy | `ResolveTenant` resolves the organization from the host. `BelongsToTenant` scopes every model and fails closed. Composite `(organization_id, id)` keys (`TenantSchema`) stop cross-tenant references at the database. |
| Switching organization | Each organization is its own host, so switching is Central's workspace switcher. The session is bound to one tenant (`RequirePlatformAccess::SESSION_TENANT`). Nothing to build. |
| Entitlement | An unentitled workspace answers 404 and a member without access answers 403, both from `platform-client`. Revocation reaches open sessions. |
| RBAC | Per-application `platform/catalog.json` (permissions, roles, separation-of-duties rules), imported by Central. Assignments are made in Central and read per request. |
| Form engine | `mel-app/app/Collect` (about 3,100 lines): XLSForm vocabulary, relevance logic, groups, personal-data masking, geopoints and mobile sync. It is app-local, not a package, and deployed in production. |
| Attachments | Procurement `Documents`: private `local` disk under `{app}/{organization}/…`, served only through an authorized controller. |
| Audit | Procurement and M&E keep an app-owned audit table with a PostgreSQL append-only trigger. |
| Numbering | Procurement `Numbers`: a per-organization sequence row locked inside the caller's transaction, plus a unique index. |
| Exports | CSV through `fputcsv`, with M&E's formula-escaping rule. PDFs through `barryvdh/laravel-dompdf` (Finance, Projects, Payroll). |
| Background jobs | The database queue plus `platform:outbox`. |
| Deployment | `ops/deploy/deploy.sh` (`PRODUCTS`, `product_dir`), with `ops/nginx/products/*.conf`, `ops/php-fpm/*.conf`, a CI job per product, and a runbook per app. |

## 2. Decision

1. **A new product, `logbook-app`.** Code `logbook`, path `/logbook`, local port :9600. Its database is `logbook`. Generated from `templates/product-app`. The domain lives in `App\Logbook`. No new frameworks or infrastructure.
2. **Identity, tenancy, subscription and roles come from Central**, through `platform-client`. Logbook holds no account, organization or billing code.
3. **A Logbook-specific field engine, not the M&E one.**
   - Extracting `App\Collect` into a package would couple a deployed application to a new one, and would bring logic Logbook must not have: relevance, groups, personal-data rules, mobile sync.
   - Logbook keeps a small engine (`App\Logbook\Fields`) that uses **the same type vocabulary** (`text`, `textarea`, `integer`, `decimal`, `date`, `time`, `datetime`, `select_one`, `select_multiple`, `yes_no`), plus `file` and `user`. Field `name` is the stable identifier, as in M&E.
   - A later shared package therefore stays possible without data migration.
4. **Hybrid storage.** Relational columns hold identity, ownership, lifecycle, dates and relations. Entry values are validated JSON, interpreted by the **immutable template version** the entry was written against. Adding a field never adds a column.
5. **Two layers of access.**
   - **Catalog (organization level)** says *what* a member may do.
   - **Logbook access** (`logbook_access`) says *where*. An open logbook is reachable by every member with the catalog permission. A restricted logbook is reachable only by members listed on it (the whole logbook, or one sheet), with a role of contributor, reviewer or viewer.
   - The catalog is the ceiling: a listing never grants more than the member's catalog permissions.
   - `logbook.manage` and workspace owners reach every logbook.
6. **Review lifecycle**, enforced on the server:
   - review required: `draft → submitted → reviewed`, or `submitted → returned → (edited) → submitted → reviewed`;
   - no review: `draft → finalized`. Finalized is never shown as reviewed.
   - Each submission is an immutable **revision**; returns never overwrite what was submitted before. Nobody reviews their own entry, and that is not configurable.
7. **References** take the form `{SHEET CODE}-{YEAR}-{000001}`, drawn at first submission from a locked per-organization sequence, with a unique index. Drafts have no reference, so the sequence has no gaps from discarded drafts.
8. **Idempotency.** Each new entry carries a client key, unique per `(organization, creator, key)`. A repeated request returns the same entry.
9. **Out of scope:** mobile, offline, notifications, scheduling, conditional logic, and integrations with other apps (§6).

## 3. Catalog `logbook` 1.0.0

| Permission | What |
|---|---|
| `logbook.manage` | Logbooks, log sheets, templates, publishing, access lists. Reaches every logbook. |
| `logbook.entries.create` | Write, save and submit entries; correct returned ones. |
| `logbook.entries.review` | Review or return submitted entries. Never one's own. |
| `logbook.view` | Read every entry in the logbooks one reaches. |
| `logbook.reports.view` | Reports and exports, within the logbooks one reaches. |
| `logbook.audit.view` | The audit trail. |

Roles: Logbook manager, Contributor, Reviewer, Viewer, Auditor, and Logbook administrator. Separation of duties: `entries.create` with `entries.review` gives a warning in Central; the app refuses self-review.

## 4. Tables

`workspaces`, `workspace_members`, `logbooks`, `logbook_access`, `log_sheets`, `log_sheet_versions`, `log_entries`, `log_entry_revisions`, `log_entry_reviews`, `log_entry_attachments`, `log_sequences`, `log_audit_events`.

- Every table is tenant-keyed with composite foreign keys.
- On PostgreSQL:
  - triggers make audit events, revisions and reviews append-only;
  - a trigger makes published template versions immutable;
  - CHECK constraints guard statuses.
- Indexes cover the filters: `(organization_id, log_sheet_id, occurred_at)`, `(organization_id, status)`, `(organization_id, created_by)`.

## 5. Risks

- **Cross-tenant access:** covered by fail-closed scoping, composite FKs, 404 for records outside reach, and tests.
- **Large exports:** CSV is streamed in chunks. PDF is capped at 500 entries, and asks for a narrower filter beyond that. Queued exports are deferred until the volume needs them.
- **Numeric reporting** runs in PHP over the JSON values of the filtered entries, capped at 20,000 entries. A typed summary table is deferred.

## 6. Deferred

- Mobile or offline capture: built afterwards, see §8.
- Notifications.
- Scheduled or expected entries per shift.
- Conditional fields.
- Amendments to finalized entries: today a correction is a new entry referencing the old one.
- Sheet-level reference formats.
- Queued exports.
- Links to Projects, HR (people) or an asset register.

## 8. Phone app (2026-11-19)

**Decision:** a separate Expo app, `logbook-mobile-app` (package `com.tatook.logbook`), for writing entries offline and for reviewing them online. Templates, logbooks, access, reports and the audit trail stay on the web.

**API (`logbook-app/routes/api.php`):** under `{workspace}/logbook/api/v1`, with the platform bearer token (`platform.api`), throttled at 300 a minute per user. Errors are JSON.

- `me`, `kit` (sheets the person writes on, with their published version, members, file limits), `sheet-versions/{id}` (published only, reachable sheets only).
- Entries, gated by `logbook.entries.create`:
  - `GET entries?since=` (own entries changed since; default 90 days; at most 500, `complete` says whether more remain);
  - `POST entries` keyed by the phone's UUIDv7 (a repeat answers the first entry, 200), on the version it was written on (`version_id`, published, of that sheet);
  - `PUT entries/{id}` from `base_revision`; `POST entries/{id}/submit` with the revision it creates;
  - `POST entries/{id}/attachments` (deduplicated by SHA-256 within the field: a repeat answers 200), `DELETE attachments/{id}`, `DELETE entries/{id}` (draft only); deletes are idempotent.
- Reviews, gated by `logbook.entries.review`: `GET reviews`, `POST entries/{id}/review` with the revision read.
- Conflicts answer 409 with a code (`sheet_closed`, `version_unknown`, `stale`, `not_editable`); the phone never retries them by itself.

**Schema:** `log_entry_attachments.sha256` (nullable `char(64)`, indexed with the entry and field). Additive; the web's uploads fill it too but are not deduplicated.

**Phone:** SQLCipher store scoped `workspace|user`; field rules ported from `App\Logbook\Fields`; outbox with backoff (30 s to 30 min); photos re-encoded (no EXIF). Details in `logbook-mobile-app/README.md`.

**Checks:** API tests `tests/Feature/ApiTest.php` (13) in `ci:check`; phone typecheck, lint and Jest (field rules, sync against a fake server that loses replies) pass. Not run on a device; no EAS project yet.
